# 技术约束（中文）

## 1. 原版游戏环境的限制

本项目依赖《红色警戒2：尤里的复仇》的真实游戏运行时，因此需要注意以下约束：

- 原始游戏并不提供官方的训练接口
- 需要通过注入、内存读取或类似桥接机制访问状态
- 不同版本和补丁会导致偏移量改变，工程可移植性下降
- 原版游戏本身并不适合直接进行大规模无头训练

## 2. ra2yrcpp 与 YRpp 的现实边界

`ra2yrcpp` 依赖 YRpp 库，实际是围绕纯净版 YR 二进制布局的逆向工程结果。

这意味着：

- 原版二进制的结构非常敏感
- 引入 Ares / Phobos / CnCNet 补丁可能产生冲突
- 注入位置必须与目标版本匹配
- 正确性依赖于游戏版本、补丁状态和运行环境

因此，项目使用“纯净副本 + 清晰验证流程”的方式来降低不稳定性。

## 3. 轨道 A 与轨道 B 不能混用

项目采用双轨设计：

- 轨道 A：OpenRA-RL，偏工程和训练效率
- 轨道 B：ra2yrcpp / pyra2yr，偏原版保真验证

这两条路线之间：

- Python 版本不一致
- 依赖库版本不一致
- 运行环境目标不同

因此不能混装到同一环境中，否则容易出现参数不兼容、运行失败或接口不稳定的问题。

## 4. 原版游戏窗口的约束

轨道 B 在真实游戏窗口中运行时，需要注意：

- 不留后台游戏进程
- 测试结束后必须清理 `gamemd` 等进程
- 窗口化运行需要兼容显示环境
- 一些热键和窗口事件可能影响自动化脚本

## 5. 训练环境的设计思路

对于 RTS 类任务，最重要的不是“绝对的原创代码”，而是：

- 是否能稳定读取状态
- 是否能稳定输出命令
- 是否能在合理步数内形成可训练循环
- 是否能给出明确的 reward 与 done 机制

因此本项目最终依赖的是：

- 统一 RL 接口
- 稳定环境抽象
- 可靠的执行和恢复机制

## 6. 工程上要谨慎处理的事项

- 不要修改原始游戏目录
- 不要在开发时随意混合补丁版本
- 不要在公开仓库中提交大体积二进制文件
- 在验证真实窗口时要清理所有相关进程
- 公开文档需要保证说明与工程配置一致

## 7. 未来工作重点

在当前阶段，最重要的不是堆砌更多功能，而是：

- 类库接口稳定
- 环境抽象清晰
- 训练入口可复现
- 原版和 OpenRA 路线彼此独立但可互相比较

这将是后续大规模扩展的前提。
